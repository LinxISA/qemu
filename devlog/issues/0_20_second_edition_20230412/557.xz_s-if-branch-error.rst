现在的问题有两个
1、在spec_mem_load()内call的printf打印的是compare_sum内部printf的内容
2、自己加了exit()之后改变了程序的逻辑，本来是运行到后面结束的（打印可以看出来），
自己加了exit()之后，程序运行到spec_mem_load()内部退出的（不是在自己加的位置退出）

分析到这里，接着用这种思路定位难度大，时间会很长，王涛建立比对函数级别的日志，在0.20的
上一版编译器和这一版本进行比对，然后确定是哪里走的不一样；
比对qemu的运行tarce需要注意的地方：
1、可以不用管库函数，两个版本glibc是一样的，而且qemu因为执行命令的字符串不一样，库函数
也会不一样。
2、-cs_call onlycall,func : 按照函数调用为粒度打印tarce
（函数调用指块是direct, indcall, call这3种类型），要注意日志实际的意义，direct有可能
跳完之后，还在该函数内部；
3、综上，要判断，哪些日志比对不一样是需要关注的，哪些是不需要的；

打印出具体的跳转的BPC之后，通过反汇编对比发现，qemu的tarce不一样，是因为两版编译器实现
的跳转方式不一样。0410版是cond+direct，现在的版本是单独就cond，又因为这个函数内
有大的for循环，所以qemu的tarce的对比，可以到看到地方都是因为跳转实现不一样，无法对比；

一个解决办法，direct先不打印，它不仅仅是call，还包括普通的块间跳转，会有差异；qemu正在
实现；

和编译器沟通之后，0410版是cond+direct，现在的版本是单独就cond --> 这个是因为开了 
-mllvm -enable-optimize-branch=true 优化选项。可以关闭优化选项之后定位（这个优化选项）
不影响正确性，就是减少了direct,减少了空块；

因为执行557测例终端会输出一些log，比如"Decompression decoder error:
Compressed data is corrupt (code 9)"，所以现在的思路是在C语言中添加打印，确认打
印上面这个字符串的原因是什么。通过gdb x86的557程序向上溯源，确定了出错的函数是
lzma_decode()。函数调用顺序如下：

..code::

    lz_decode
        decode_buffer
            lzma2_decode
                lzma_decode

现象：lzma_decode()会被重复调用，第一次被调用的时候，进入的参数值、返回值和0410
版本编译器(联调通过的版本)一致。紧接着第2次被调用时，进入的参数值不一样了，返回值
也不一样。接下来溯源了一下第2次调用时传入的参数，发现是第一次计算的结果，大概逻辑
如下：

..code::

    lzma_decode()
    {
        ...
        // 第1步：coder作为输入的数据
        uint32_t rep0 = coder->rep0;

        uint32_t rep2 = coder->rep2;
        uint32_t rep3 = coder->rep3;

        // 第2步：对rep0/1/2/3进行计算
        ...


        // 第3步：保留计算的结果到coder中，以便下一次计算作为输入数据
        coder->rep0 = rep0;
        coder->rep1 = rep1;
        coder->rep2 = rep2;
        coder->rep3 = rep3;
        return
    }

qemu log）。如下：
