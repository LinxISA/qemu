400.perlbench测例分析
********************

介绍
======
SpecInt2006测例中，400.perlbench子项在用LLVM-v0.20 Hyper优化第一版编译器编译后，
在qemu上运行遇到了段错误的问题。

本篇就是用来记录 400.perlbench 问题分析的情况。

分析
======
1、首先通过gdb调试qemu运行400测例的程序跑到段错误的位置，然后打印host的pc。
根据这个pc去qemu日志中找对应的blockisa编译后程序内bpc或tpc。

qemu段错误位置::

    Thread 1 "qemu-linx" received signal SIGSEGV, Segmentation fault.
    0x00007fffe8f86b33 in code_gen_buffer ()
    (gdb) p/x $pc
    $1 = 0x7fffe8f86b33

bisa发生段错误的pc::

    -- guest addr 0x00000000000f265a
    0x7fffe8f86b33:  0f b6 1b                 movzbl   (%rbx), %ebx
    0x7fffe8f86b36:  48 89 9d e0 06 00 00     movq     %rbx, 0x6e0(%rbp)

bisa发生段错误的指令对应的pc为：0x00000000000f265a

根据pc，在qemu日志中找到发生段错误的指令::

可以找到产生段错误指令为：lbu [t#1, 0]。

可以看到该块是个hyper块，lbu的地址与 a0 和 ra 寄存器有关。
查看前面的日志发现该块循环执行了多次，每次a0的值是有规律变化的，但是在发生段错误的这次循环中，
a0的值发生较大变化，变的完全无规律。

发生段错误的指令仍然是：lbu  [t#1, 0]，位置与更新前也是一样的。
同时需要注意的是该块是条件跳转块，条件成立后会跳回到本块重新执行，也就是一个循环块，
循环次数是256，循环变量是a0的值，每次循环加1。

单步打印一下该块内每条指令执行前后寄存器的状态，查看此时a0与ra寄存器的值。
下面是发生段错误的那次循环a0与ra寄存器的值。

	ld              [sp, 40]
	set.lgpr        t#1, ra
	get             a0					//T3      <-532749
	andi            t#1, 7
	srli            t#2, 2				          <- a64e9
	get             ra					//T6      <- 532748
	add             t#1, t#2			          <- 5d8c31
	lbu             [t#1, 0]			//T8

可以看到ra寄存器的值是通过ld得到的，块内也没有对该地址做修改，所以ra的值在循环内是不变的。

向上查看qemu日志，观察ra寄存器的值确实是不变的。但是a0的值发生段错误的这次发生了无规律变化。

再向上找发现a0的值是依次递减的(0x61->0x60->0x5f.....)，符合前面判断的循环变量的变化规律。

从上面块内微指令序列我们可以看到，a0可能会发生两次修改。

第一次::

	0x00000000000f2604:  0539              ld              [sp, 40]
	0x00000000000f2606:  0267              set.lgpr        t#1, a0

第二次::
    
    0x00000000000f261a:  20e6              get             a0
	0x00000000000f261c:  0101              addi            t#1, 1
	0x00000000000f261e:  0267              set.lgpr        t#1, a0

下面这个修改是循环迭代a0每次加1，上面修改完全覆盖了a0原来的值。
查看日志发现由于块内存在块内跳转指令bc和bci,前面a0正常变化时块内跳转指令判断都是成功的，
跳过了第一次对a0修改的位置，所以a0每次循环正常加1，但是发生段错误的前一次块的执行中，
bc和bci指令都判断失败，没有发生块内跳转，导致a0在第一次修改的位置被覆盖了。
最终导致在下一次该块的执行中a0的值有问题，导致地址计算出错，lwu指令发生段错误。
