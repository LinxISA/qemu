根据输出，发现从标准输出第四列 2362 开始，执行测例输出开始比标准输出数值大。

首先定位确定此段输出在源码中的位置，确定到 utils.cpp 文件 post_thinking()
函数内::

    myprintf("%2d %7d %5d %8llu  ",gamestate.i_depth,score,elapsed,s->nodes);

可以看到是 s->nodes 数值存在不同；
在项目内找到 s->nodes 此值变化有两处，均为 s->nodes++；

接下来的定位方法：添加打印，对比 016 & 020两文件 s->nodes 值变化，根据打印信息，
再打印 qemu 执行日志，对比寄存器信息，逐步定位。

添加打印::

    printf("search_s->nodes: %llu\n", s->nodes);
    printf("search_s->nodes: %llu\n", s->nodes);

发现在s->nodes是2138的时候::

    020：

    qsearch_s->nodes: 2139

x86中的s->nodes是2138的时候，在qsearch的这个位置会退出，但在0.20不会，再缩小范围；

找到在 qsearch() 函数内调用  ProbeTT() 的返回值是不一样的，再添加打印::

    bound: 0, alpha: -30, beta: 30, best: 0, xdummy: 0, xdummy: 0, xdummy: 0, xdummy: 0

看到 ProbeTT() 函数返回值是不一样的，即x86 中，ProbeTT 函数的返回值为4，而在020中的
返回值为0。

范围缩小到 ProbeTT() 函数内，对比发现::

    if (temp->buckets[i].hash == nhash)

从这可以看到是这句右移指令导致 020 与 x86 nhash3 值不同
接下来找下这条右移微指令。

打印 qemu 执行日志，比对 016 与 020 寄存器信息变化::

    016
    r6/s1    c44dc3e4635f944e -> r6/s1    00000000c44dc3e4

    020
    r6/s1    c44dc3e4635f944e -> r6/s1    0000000000000000

根据 trace 信息可以看出，016 在数据移位之后值正确，020 移位之后数据为0，
定位到是 qemu 的 remuw 指令导致的结果出错。
