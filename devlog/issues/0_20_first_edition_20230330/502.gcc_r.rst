502.gcc_r 执行问题分析文档
***************************
作者:y30042171(杨继钦)

问题描述
========
502.gcc_r qemu运行之后报错的问题

问题分析
========
20230329

这个spec测例的可执行文件是一个编译器，我的理解就是这是个编译器测例。先用llvm的编译器
编译出来可执行文件，这个文件拥有编译功能，能把.c编译成.s文件，现在是这个执行过程
报段错误。

先看执行过程的报错，这个执行过程中，出现的不一样的地方就是，走到了gt_pch_na_fde_table
这个函数挂的，但是为什么挂，我的理解是很难得到，因为现在编译器是编译出来的，不受
我们控制，qemu只是给这个编译器提供了环境，来让它编译，但是它为什么编译挂，qemu是一无所知
的。

所以这就比较独特，先考虑qemu的执行流，对比一下，两个版本的编译器，分别走了什么执行流，
才导致了不一样的结果（不过这个执行流相当大）。所以有可能是指令执行不一致的问题，load类
指令和store类型指令可能有编译器和qemu不一致的地方，这个事情可以排查一下，再跑遍502.

排除发现没有问题，从头看看0.16跟0.20的差异，先尝试看函数的调用栈，从头看下来，
从_dl_discover_osversion函数开始，两者就出现了调用的差异，0.20的调用顺序看下来，
有memset->strrchr->expandargv这个路径，但0.16已经过去了expandargv还没有出现memset，
在0.16出现第一次memset的情况下，0.20已经出现第二次。也就是这两个版本都有toplev_main
到xmalloc再到calloc再到memset这一路径，按理来说不应该出现这个差异。所以先确认一下
打印的方式是否一致（执行函数），然后再确认一下出现这种调用差异的情况是否合理。

这个差异有可能是编译器的原因，编出来的程序执行顺利不一致了，也有可能是qemu打印相应
调用函数是否合理，以及这种比对方式是否有效，如果这种差异的存在是合理的可能就需要
及时改变方法了。

从报错信息来看，出错的函数是gt_pch_na_fde_table这个函数，考虑构建一个gt_pch_na_fde_table.c文件，
这个文件中加上gt_pch_na_fde_table的相关依赖，单独编译这个.c，看看能不能复现问题。

成功构建了这样的文件之后，重新执行，发现问题是一样的，这时的日志已经小了，可以看看
出错的问题在哪，可以看到在99b730这个块之后，qemu跑到了80000这个pc值，但是这个pc可以
在反汇编看到是不存在的，所以问题显然已经找到，就要分析一下do_per_function以及相关
函数的反汇编代码以及qemu执行的日志，看看出错的地方到底是哪里。

99b730这个块之所以跑到80000这个pc值，是因为这个块是个indirectly call类型的块，它跳到

用s0这个寄存器里面的地址进行跳转，所以可以加个打印，看看在pc处于99b730这个块的时候，
s0寄存器的变化，可以发现的确是80000，那么qemu的执行看起来符合预期，就得看看汇编逻辑了。

然后从这个块看出来，s0的值没变，store和load的只是暂存了一下s0的值。所以这个块用s0
进行pc的设定，这个问题可以确认一下。

经过编译器的确认，s0作为地址确实有问题，结论如下：

tail indirect call作为函数退出语句时，需要一个寄存器作为输入指定其目标地址。
Epilogue在函数退出语句前会还原Callee Save寄存器(CSR)。如果tail indirect call
被RA分配了CSR，插入Epilogue时就会污染这个寄存器的值。在RISCV中，解决方法是声明
一个不包含CSR的RegClass提供给tail indirect call使用，在BlockISA中，可以直接使用
T寄存器作为其输入。

重新出一版编译器之后，这个问题解决。
