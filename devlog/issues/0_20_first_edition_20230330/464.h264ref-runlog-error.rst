********************

介绍
======

log与riscv以及arm的输出不一致（在保证运行命令及输入文件一致的基础上）。

本篇就是用来记录 464.h264ref 分析的情况。

所以打印这两个变量的相关值。
注：edge_cr和StrengthSum是int型变量，chroma_edge是char类型三维数组。

	{ { {-1, 0, 0, 0},
		{-1,-1,-1, 1},

x86截取输出::

	StrengthSum:3

arm、rv和bisa截取输出::
	edge_cr:255,dir:0,edge:1,img->yuv_format:1,chroma_edge:255
	StrengthSum:3

可以看到当chroma_edge数组内值为-1时，从char类型到int型的赋值，x86是正常的，
其他三个是错误的。

我们知道，char类型占1字节，-1则表示为0xFF。而int型占4字节,255则表示为0x000000FF。
所以这里怀疑arm等编译器在char类型向int类型赋值时，
做了零扩展，而x86采用了正确的有符号扩展。

为了验证这个想法，手写一个小测例::

结论
=====
不同的架构对char类型的处理不一致，arm、riscv和bisa的编译器会默认char类型变量是无符号的。
而x86则默认是有符号的。所以本测例中，char类型数组元素向int型变量赋值过程中bisa做了无符
号扩展，导致赋值后有问题，影响了最终结果。编译时通过添加-fsigned-char编译选项解决。
