520.omnetpp_r功能验证失败分析文档
*********************************
作者:wwx1207825(吴志威)

问题描述
=========
20230329

520 子项从官方文档介绍来看，是模拟一个 10 GB 的网络通信，该网络由六个骨干交换机、八个小
型局域网、二十个中型局域网和十二个大型局域网组成。该子项有两种输入文件，NED 文件以及
omnetpp.ini。NED 是 OMNeT++ 的网络描述语言用来描述网络设备的各种参数，设备的具体操作
是写在代码中。omnetpp.ini 用来指定该模型的一些参数，比如说：sim-time-limit 用来设置
模拟时间。

模拟运行结束后，会有个输出文件 General-0.sca，统计各个设备在模拟过程中的一些信息，比如
网络层的接收包的数量、数据链路层的接收帧数量。当前(2023/4/11)只有 gcc 支持 C++ 异常，
所以该子项一开始只用 gcc 编译并运行。

使用0.20的gcc编译该子项后，可以在qemu上成功运行对应的可执行文件，运行结束后会在屏幕上
打印一些运行的log，同时还会生成一个叫做General-0.sca的文件，而该子项的功能验证需要让
该文件和标准输出文件进行比对，二者完全一致时才算是功能验证通过。在比对了0.20的输出文件
和标准输出文件后，发现有非常多的不同之处。

切换到0.16的gcc编译该子项并在qemu上跑，输出文件也不同，于是转而定位0.16gcc的错误。


错误定位
=========

1. 由于输出的sca文件不同之处太多，导致无从下手，于是转而比对0.16的log和x86的log，发现
   是在Cmdenv::printEventBanner函数中的打印不一致，而不一致的输出来源是simulation.getEventNumber
   函数，该函数会返回event_num；转而寻找event_num在何处被改变，发现该变量只在cSimulation::doOneEvent
   函数中会进行++的操作，于是继续寻找在何处调用doOneEvent函数；发现在Cmdenv::simulate
   函数中会调用doOneEvent，而simulate正是520子项的主体函数之一，于是先分析该函数。

2. simulate函数主体被一个try-catch包裹，try块中含一个if-else，在if-else语句中存在
   while循环，循环中会调用doOneEvent函数，在doOneEvent函数调用后边加上一个count++，
   来查看调用的次数，发现该函数的调用0.16和x86不一致，即while循环的执行次数不一致；于
   是转而查找该while循环的退出方式，发现只可能是通过throw语句抛异常来退出的while循环，
   于是在catch块中加入打印验证该猜想，发现果然是有一次的catch异常，且只有一次；于是转
   而查找是在哪里抛出的异常，在while中所有throw语句中加打印，发现都不执行，而是在其中
   的checkTimeLimits函数中抛出的异常，于是转而分析该函数。

3. 在checkTimeLimits函数中加入count++，查看该函数的执行次数，发现0.16比x86少，转向
   该函数的throw语句，将执行throw语句的条件中的相关变量的值全部打印出来::

    if (opt_simtimelimit!=0 && simulation.getSimTime()>=opt_simtimelimit){
        std::cout<<std::endl<<"here1: "<< count << std::endl;                   
        std::cout<<"opt_simtimelimit: "<< opt_simtimelimit<<"  simulation.getSimTime():" << simulation.getSimTime() << std::endl;        
        throw cTerminationException(eSIMTIME);
    }

   发现getSimTime的值，0.16和x86不一致，而该函数会返回sim_time，再让sim_time和
   opt_simtimelimit进行比较，若相等则抛异常从而结束整个simulate，打印发现opt_simtimelimit
   的值固定为0.003，后续又发现该值是在520子项的一个ini文件中进行设置的，可以手动修改。
   转而查看sim_time在何处被修改，发现该值来源于*cSimulation::selectNextModule函数中
   的msg->getArrivalTime()函数，该函数返回delivd，转而查看msg对象在何处被修改，发现
   有若干函数均对该值进行了修改，统统加打印，对比0.16和x86，发现在带三个参数的cMessage::setArrival
   函数中，delivd的值发生了改变，而该函数又是把参数t赋给了delivd的，接着往上捋函数调
   用关系。

4. 在cSimpleModule::scheduleAt中调用了msg->setArrival函数，而参数t又来自scheduleAt
   的参数t，往上找scheduleAt，发现EtherAppCli::handleMessage调用了scheduleAt，在其
   中打印所有相关变量的值，发现waitTime->longValue()的值0.16和x86不一致，进入longValue
   在其中打印所有相关变量的值，发现v.dbl的值0.16和x86不一致，而该值是在evaluate函数中
   被修改的，转而分析evaluate函数。

5. evaluate函数中含许多switch语句，都加上打印捋清运行的路径，最终确定会走到case Elem::NEDFUNC:
   处，并在此处进行相关变量的值的修改，且0.16和x86不一致，而出错变量的值又是通过invoke
   函数进行修改的，进入invoke函数::

    cDynamicExpression::Value cNEDFunction::invoke(cComponent *context, cDynamicExpression::Value argv[], int argc){
        checkArgs(argv, argc);
        return f(context, argv, argc);
    }
   
   发现是argv处出错，而f是一个函数指针，最终确定会调用到intuniform函数，该函数的返回
   值会赋给argv[0].dbl，导致dbl值出错，转而查看intuniform函数，该函数的返回值又由
   genk_intrand函数间接决定，再转向genk_intrand函数，该函数的返回值又由intRand函数
   决定，再转向intRand函数，该函数的返回值又由rng.randInt函数决定，接着分析rng.randInt
   函数。

6. 打印randInt函数中所有相关的变量值，发现在pNext变量处0.16和x86的值就有不同，往上捋
   发现pNext在reload函数内被修改，继续梳理函数调用逻辑发现，reload函数被俩参数MTRand::seed
   函数调用，而俩参数seed又被无参数seed调用，俩参数seed函数中还会调用initialize函数，
   在俩参数seed函数中打印相关变量的值，发现state数组的值0.16和x86不一致，而state数组
   的值来自于bigSeed数组，往上找bigSeed数组在何处初始化，发现是在无参数seed函数中，bigSeed
   数组被赋初值，且数值来源于/dev/urandom文件，该文件提供随机数。

   在initialize函数中的for循环中加入一行fflush（）后，发现子项的输出正确了::

        }
    }

从志威上的分析来看，在 initialize 中加上 fflush 后，就会导致该测例验证通过，去掉后，测
例又会验证失败。我感觉这像是编译器优化导致的问题，将编译参数中的 O3 换成 O2 后，重新编译
运行，验证是能通过的。所以，我想是不是 O3 比 O2 多了个啥优化选项，导致验证不通过，那可不
可以单纯的比较 加参数 和 不加参数 汇编的区别，看看能不能确认这个问题。

从 gcc 的文档来看，可以通过以下命令来显示 O3 所开启的优化选项::

    gcc -Q --help=optimizers -O3

然后，就是一个个的来测，看看是哪个参数导致的，最后试出来是 -fpeel-loops，比对了下汇编，
差异还是好大，看不出来啥，还是老老实实的在程序里面打桩。

基于志威的分析，他定位到是在 seed 函数出现了，seed 函数定义在 mersennetwister.h 中，

这样看起来是 createOne 函数里面修改了这个寄存器的值，这就有些奇怪了，s5 寄存器在修改
abi 前是一个 callee save 的寄存器，按道理 createOne 或其调用的函数要使用 s5 前应该保
存下 s5，在返回的时候恢复 s5。假设 abi 修改后，s5 变成了 caller save 的寄存器，在
createOne 返回的时候，也应该要把 s5 恢复，但从汇编上看是没有的。我这边没法再继续往下看，
得先问下编译器。

问了下编译器的同事，s5 是 caller save 的，还是 callee save 的寄存器，那边没有直接回答，
让我看下 readPerRunOptions 里是不是在函数入口处 save 了 s5。从汇编上看，这个 s5 是在
这个函数开始的时候 save s5，那这样看来，abi 修改后，s5 寄存器任然是一个 callee save。

之后，就得确认 s5 修改的那个函数，是否有保存 s5。还是通过 QEMU 日志，在 for 循环的前后
加上 enable_log 和 disable_log 的功能，确定到是在 seed() 函数修改了这个值，而且从
函数上看，也没有保存这个 s5。反馈给编译器后，他们的回复是这样的::
