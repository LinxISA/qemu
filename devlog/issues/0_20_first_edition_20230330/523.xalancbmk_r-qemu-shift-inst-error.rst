523子项qemu移位指令实现有误溯源
*******************************

介绍
====

本篇主要是记录并分析 v0.20+523.xalancbmk 子项specint执行、功能验证过程中出现的问题，
以供后来者了解情况。qemu分支：linx-dev-performance-0.20

分析人：韩志林 h30043474

现象
====

下面记录的问题一一按序出现：

1. 执行出现段错误；(编译器sysset操作数data,addr位置理解反了)
2. 执行陷入循环，在2个块中间循环执行；(编译器sc操作数data,addr位置理解反了)
3. 执行出现 Aborted (core dumped)；(qemu移位指令移位位数实现有误)
4. 执行小测例运行到qemu中的 g_assert_not_reached() 部分。(tail indirect call)

错误定位+解决方案
=================

1. 执行出现段错误。这种段错误的问题定位较好定位，一般是访存指令产生的。可直接查
   看对应的微指令。定位到是一个 sysset 指令导致的段错误，查看 sysset 两个操作数
   的值其中有一个是通过 lwu.ip 取出的 0x800，一个是不规律的较大值(类似这种0x3fad)
   的值，实际执行的操作是要将 0x800 这个data放到csr[0x3fad]中，发生了段错误。考
   虑到 1、objdup 反汇编出是"sysset t#1, t#2"这种格式，qemu反汇编出的是 "sysset t#2, t#1"
   这种格式；2、0x800是UTPR这个csr的编号；所以怀疑是sysset指令编译器那边的理解可
   能和定义有出入，经过沟通确认，是编译器编译出的sysset操作数理解反了，编译器修
   复该bug后该问题解决。
2. 执行陷入循环。在2个块中反复执行。查看微指令，有一个块中有 sc.w.aq t#2,[t#1]
   这条指令；另外一个块中有 lr.w [t#1]这条指令，结合qemu反汇编出的是 "scw.aqrl t#1,[t#2]",
   也怀疑是编译器将sc.w指令的"data"和"addr"理解反了，临时修改qemu，"将错就错"尝
   试一下发现，该问题消失。和编译器沟通之后，编译器确认是该问题，修复后该问题解决。
3. 执行出现 Aborted (core dumped)；定位到在重复的执行和异常相关库函数。最后发现
   是qemu的移位指令的位数有误。询问白晓瑞，发现定位过程是和 623_xalancbmk_0_13_beta.rst
   这里分析的过程一模一样，最后都是定位到 "1<<(k&0x1F)" 这个计算结果不对(可结合
   623_xalancbmk_0_13_beta.rst 分析)，现象也是和编译器修复之前 623_xalancbmk_0_13_beta.rst
   的一致，都是移位位数超过 32，结果就会不符合预期。进一步发现 "sllw t#1,t#5" 的
   t#5的值如果大于32，结果会不符合预期，检视qemu代码实现，发现qemu实现的带"w"字
   样的移位指令有bug，定义上，如"sllw t#l,t#r"，其移位位数有限制，为 t#r&0x1f;
   qemu的实现是t#&0x3f, 修复该bug后，该问题解决。qemu实现错误的原因是 sllw 的指
   令参考64bit的sll指令的实现，sll的移位位数是 t#2&0x3f, 缺少自测导致该问题出现。
4. 执行小测例运行到qemu中的 g_assert_not_reached() 部分。查看qemu源码发现是翻译
   到了一个未定义的块类型。怀疑执行该子项跑飞了，通过gdb调试打印当前bpc，为0x9d6510,
   打印块类型，确定确实是一个未定义的块类型。通过objdump查看地址最大的块也比0x9d6510
   要小，确定是执行跑飞了。继续gdb调试，设置当下一个bpc==0x9d6510时的条件断点，
   打印此时的bpc(0xbc7f0)，也就是跳到异常bpc的上一个bpc，得到上一个bpc的值后查看
   反汇编中的块跳转类型和微指令，发现跳转块类型是indcall，最后一条微指令是
   "setc.tgt s0"。这个时候通过qemu执行参数 "-dfilter addr0..addr1"单步执行，打印
   出该块中每一条微指令的执行结果，发现并无异常，数据在该块中来源正常，需要继续
   向上溯源异常bpc(0x9d6510)的数据来源。后续specint问题对齐过程中，确认 502.gcc_r
   的执行不通过和523这个子项的该问题一致，编译器修复该bug后该问题解决。

   ..note::

        第4点，编译器解决的问题如下：tail indirect call作为函数退出语句时，需要
        一个寄存器作为输入指定其目标地址。Epilogue在函数退出语句前会还原Callee Save
        寄存器(CSR)。如果tail indirect call被RA分配了CSR，插入Epilogue时就会污染
        这个寄存器的值。在RISCV中，解决方法是声明一个不包含CSR的RegClass提供给
        tail indirect call使用，在BlockISA中，可以直接使用T寄存器作为其输入。
