429.mcf子项切片数据异常问题分析
*******************************
作者:zwx1144326

问题描述:
==========
0.13版llvm编译器生成的切片, 比20221102版llvm编译器生成的切片,light_model运行的指令数和cycle数多了近一倍。

分析:
======
0.13llvm编译器版本信息:
clang version 12.0.0 (Linx Block ISA VXXXRXXXCXXBXXX clang-3bbab144d1ba flang-3bbab144d1ba)
Target: x86_64-unknown-linux-gnu
Thread model: posix
InstalledDir: /remote/lms04/zwx1144326/BlockISA/linx64_Compiler/linx_blockisa_llvm-0.13-fix-ext/bin

20221102版llvm编译器版本信息:
clang version 12.0.0 (Linx Block ISA VXXXRXXXCXXBXXX clang-ba7615dfb6a3 flang-ba7615dfb6a3)
Target: x86_64-unknown-linux-gnu
Thread model: posix

确定是不是自己操作失误的问题::
    可执行文件的反汇编和切片的执行trace进行对比,BPC和TPC是对应的,不是自己操作的问题；
    (之前有人因为操作失误,导致qemu跑的可执行文件,和生成的切片不是一个东西,所以增加这样一个校验过程)

静态指令数是否增加::
    查看0.13版llvm和20221102版llvm编译的二进制反汇编,分析是不是静态指令数增加,导致生成切片指令数增加

    kernel函数是:primal_bea_mpp(),内部调用了两个函数:sort_baske(),hotspot(),统计这三个函数的静态指令数。
    统计方法:(函数最后一个块头的ptr-函数第一个块头的ptr)/2 + 函数最后一个快头的指令数
    统计结果:(old是20221102版llvm编译器编译可执行文件的反汇编,new是0.13版llvm编译器编译可执行文件的反汇编)
    primal_bea_mpp
    old: (127b4-12542)/2+11=272(626)/2 +11
    new: (1308e-12e38)/2+d=256(598)/2+d  
    sort_basket
    old: (12462-12362)/2+1b=100(256)/2+1b
    new: (12d70-12c7c)/2+12=F4(244)/2+121
    hotspot
    old: (1253e-12498)/2+2=A6(166)/2+2
    new: (12e34-12d94)/2+2=A0(160)/2+2
    比对结果:静态指令数没有大的差别；

确定函数调用次数是否正确::
    统计切片执行tarce流中,call sort_baske(),hotspot()的次数,和x86的进行比较是否一致
    统计结果(old是20221102版llvm切片,new是0.13版llvm版切片)
    sort_basket
    old: 16次
    new: 26次 
    hotspot 该函数被内联到了kernel函数内
    比对发现old和new的切片,调用sort_basket()函数的次数不一样,统计x86改函数的调用次数(通过函数内部加打印的方式统计)
    sort_basket()在x86的调用次数:26次

结论:
=====
    20221102版llvm编译器编译生成可执行文件有错误,导致sort_basket()函数调用的次数和相比x86的(认为源码是正确的,x86的编译器是正确的)调用次数有减少,
    所以0.13版llvm编译器生成的切片, 比20221102版llvm编译器生成的切片指令数增加.
    和编译器确认,没必要分析20221102版llvm编译器编译生成可执行文件具体什么原因,导致了这个错误,分析出来对现在的编译器也没有多大的参考价值；
