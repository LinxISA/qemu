401.bzip2子项切片0.13beta异常问题分析
**************************************

问题描述：
==========
用0.13beta llvm编译器编译401.bzip2测例生成了可执行文件后，用qemu跑该可执行文件会提示错误信息：
(null): Data integrity error when decompressing.

本篇记录了该问题的分析过程，分析人：吴志威

分析：
======
1、401测例执行的功能是文件的压缩与解压，根据报错信息找到提示错误的函数：crcError()，顾名思义，
可初步猜测是crc校验码出错::

   static void crcError ( void )
   {
      fprintf ( stderr, "\n%s: Data integrity error when decompressing.\n",progName );
      。。。
   }

2、往上理，发现是uncompressStream()这个函数goto到了errhandler，然后调用了crcError()，而goto的
原因是 “bzerr!=4”；分析可知，变量bzerr是用来记录压缩和解压过程中的出错种类信息的，而出错时，bzerr
的值为-4，错误种类为BZ_DATA_ERROR::

   Bool uncompressStream ( int zStream, int stream )
   {
   。。。
      if (bzerr != BZ_STREAM_END) {
         fprintf(stderr,"\n%s: goto errhandler here2. bzerr:%d\n",progName,bzerr); //modified
         goto errhandler;
      }
   。。。
   }

3、往上找bzerr被改变的地方，发现bzerr的值在BZ2_bzRead()中被修改，进入BZ2_bzRead()，发现bzerr被
赋值成了BZ2_bzDecompress()的返回值，而BZ2_bzDecompress()返回了一个-4::

   。。。
   ret = BZ2_bzDecompress ( &(bzf->strm) );
   if (ret != BZ_OK && ret != BZ_STREAM_END) {
      BZ_SETERR(ret);
      if (*bzerror == -4) fprintf(stderr,"\nbzerr in bzlib change to: %d\n",*bzerror);  //modified
      return 0;
   }
   。。。

4、进入BZ2_bzDecompress()，在这个函数里面加几个printf，看看他的执行流程是怎样的::

   。。。
   fprintf(stderr,"1");     //modified
   if (s->smallDecompress)
      {printf("s"); corrupt = unRLE_obuf_to_output_SMALL ( s ); }   //modified
   else
      {printf("f"); corrupt = unRLE_obuf_to_output_FAST  ( s ); }   //modified
   if (s->nblock_used == s->save_nblock+1 && s->state_out_len == 0) {
      printf("2");     //modified
      if (s->calculatedBlockCRC != s->storedBlockCRC) printf("\n两个crc码不等");   //modified
   。。。
      if (s->calculatedBlockCRC != s->storedBlockCRC){
         printf("\nhere2. calculatedBlockCRC:%d storedBlockCRC:%d",s->calculatedBlockCRC,s->storedBlockCRC); //modified
         return BZ_DATA_ERROR;
      }
   }
   。。。

通过log可知，函数走到了unRLE_obuf_to_output_FAST()，然后进入了下面的if内，正常情况下，函数不会
走进该if：if(s->calculatedBlockCRC != s->storedBlockCRC)；但是发生错误时，函数走进了该if，
即出现了s->calculatedBlockCRC != s->storedBlockCRC 的情况。

5、打印s->calculatedBlockCRC 和 s->storedBlockCRC的值，再和x86的输出进行对比:

   linx的结果::
      calculatedBlockCRC:-538858166 storedBlockCRC:1737343573
      3
      calculatedBlockCRC:-538858166 storedBlockCRC:1737343573
      3
      calculatedBlockCRC:-1 storedBlockCRC:1737343573
      1f
      calculatedBlockCRC:-716648556 storedBlockCRC:1737343573
      1f
      calculatedBlockCRC:818747916 storedBlockCRC:1737343573

   x86的结果::
      calculatedBlockCRC:-538858166 storedBlockCRC:1737343573
      3
      calculatedBlockCRC:-538858166 storedBlockCRC:1737343573
      3
      calculatedBlockCRC:-1 storedBlockCRC:1737343573
      1f
      calculatedBlockCRC:829596189 storedBlockCRC:1737343573
      1f
      calculatedBlockCRC:383783449 storedBlockCRC:1737343573

发现calculatedBlockCRC的值在x86侧和blockisa侧的变动不一样，而通过上面梳理的函数执行流程可知
calculatedBlockCRC的值是在unRLE_obuf_to_output_FAST()中被改变的。

6、进入unRLE_obuf_to_output_FAST()，首先确定该函数的执行流程，并确定calculatedBlockCRC是如何
被改变的::

   while (True) {
      。。。
      PMC_START();
      fprintf(stderr," calculatedBlockCRC:%d ",c_calculatedBlockCRC);    //modified
      BZ_UPDATE_CRC ( c_calculatedBlockCRC, c_state_out_ch );
      fprintf(stderr," calculatedBlockCRC:%d ",c_calculatedBlockCRC);    //modified
      PMC_END();
   }
   。。。

发现calculatedBlockCRC是在BZ_UPDATE_CRC()中被重复进行更改，以下是BZ_UPDATE_CRC()函数的源码::

   #define BZ_UPDATE_CRC(crcVar,cha){
      crcVar = (crcVar << 8) ^  BZ2_crc32Table[(crcVar >> 24) ^ ((UChar)cha)];}

7、确认是在该函数中，calculatedBlockCRC的值变动错误，在该函数前后打印calculatedBlockCRC的值，
并加上汇编的标记，获得该函数的汇编代码:

以下是BZ_UPDATE_CRC()函数的反汇编::

      0000000000017442 <.LBB10_163.bstart>:

      17444:	1fe1                	slli	t#1,32
      17446:	1fa1                	srli	t#1,32

以下分别是x86和blockisa在BZ_UPDATE_CRC()函数前后calculatedBlockCRC的值::

   linx的结果：
      。。。
      calculatedBlockCRC:-1  calculatedBlockCRC:-1  calculatedBlockCRC:-716648556  calculatedBlockCRC:-716648556
   x86的结果：
      。。。
      calculatedBlockCRC:-1  calculatedBlockCRC:-1  calculatedBlockCRC:829596189  calculatedBlockCRC:829596189

可以看到，该函数存在若干移位指令，且x86和blockisa两侧的数据在经过了这段运算操作后，他们的值变的
不相同了，所以推测是数据在移位操作过程中发生了错误；再加上存在其他测例的出错原因是编译器对移位指
令的处理不对导致的，所以此处推测401的问题也是移位指令出错导致的；等待编译器发出一版移位指令修复
的版本，再看看问题是否还存在。

8、根据编译器方的确认，得知错误根本原因是一个移位指令的bug，编译器本该生成sllw，却生成了sll，而
二者的功能存在差别，这才导致数据在移位操作后出现错误。在拿到修复后给出的新版本编译器后，该测例能
正常执行通过，暂无必要继续定位，后续如果还存在问题再继续看看。

sll：将左源T寄存器中的值逻辑左移右源T寄存器中低6位的值加1，结果写到目的T寄存器中。
sllw：将左源T寄存器中低32位逻辑左移右源T寄存器中低5位的值加1，结果写到目的T寄存器中。

现状：
======
更换修复移位指令版本的编译器后，401的问题确认解决，在标准输入文件下，x86 和 blockisa 的输出均
一样。
